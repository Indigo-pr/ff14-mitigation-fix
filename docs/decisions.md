# 設計判断とその理由

「なぜこうなっているか」の記録。将来いじるときに壊さないための覚書。

---

## 軽減表そのものは作らない

最初は「ログから軽減表を生成するツール」を作ろうとしていたが、調べた結果：

- 軽減スキルDB（ジョブ別の軽減率・効果時間・リキャスト・対象範囲）は既存テンプレートに**全部入っていた**
- タイムラインのFFLogs自動生成も**ジェネレーター本体に標準搭載**されていた

作るべきものは新しいツールではなく、**生成結果の検算・補正**だけだった。

## 種別は推測しない

当初は「頭割り / 全体 / タンク強攻撃 / 単体」を自動判定していたが廃止した。

理由: FF14の頭割りは「4人」「2人」「タンク以外の6人」などバリエーションが多く、
**対象人数が変動するログでないと判定できない**。
零式を綺麗に消化したログは人数が固定なので判定材料がない
（今回シルキーで判定できたのは全滅間際で人が減ったため、という皮肉な事情）。

現在の種別は観測事実だけ：

| 種別 | 条件 |
|---|---|
| 通常攻撃 | 技名が `AA_NAMES` に一致 |
| 単体 | 常に対象1人 |
| 複数対象 | それ以外 |

**断定する代わりに、判断材料をメモに全部出す。**
回ごとの「時刻 / 対象数 / 最大値」が並ぶので、人数が減るほど値が上がる＝頭割り、と人が読める。

## 通常攻撃は技名で判定する

発動間隔（3秒おきに繰り返す）で推測していたが、名前判定に変えた。

理由: **タンク強攻撃には必ず固有の技名が付く**ため、
「攻撃 / Attack」という名前のものは全てAAと断言してよい。推測より確実。

## AAだけ中央値を採る

AAの実測値は `3,416 / 7,039 / 14,768 / 15,327 / 23,292 / 34,568` と3倍以上ばらつく。
ブロック20%・受け流し15%が毎回ランダムに絡むため。

ここで最大値を採ると 34,568 になるが実態は15,000前後。
**AAは継続的なチップダメージであって軽減計画の対象ではない**ので、
安全側より代表値の方が役に立つ。他の技は最大値のまま。

## 複数対象は「対象人数が最も多かった回」を採る（PICK_MODE='fullest'）

単純な最大値だと、すべってシャンプーボムは2人時の **94,969** になる。
だがこの回は全滅間際で人が減っていた状態であり、
そこを基準に軽減を組むと表が常に真っ赤になって使い物にならない。

「人が最も揃っていた回＝意図した処理」とみなして、その回の最大値を採る。
安全側に振りたい場合は `PICK_MODE = 'max'` に変えられるようにしてある。

## 1,000単位で切り上げる

±5%の乱数がある以上、**観測した最大値がその技の上限とは限らない**。
参考にしたM9Sのシートも 90,000 / 105,000 / 620,000 と全部5,000刻みで、
作者が公称値を手で丸めて入れている。

軽減表に入れるべきは「ある1回の実測値」ではなく「安全側に丸めた設計値」。
切り上げることで安全マージンと見やすさが同時に手に入る。

## Action列にタグを付けない

一時期 `すべってシャンプーボム【頭割り4人】` のように書いていたが、
シートが読みにくくなるためやめた。種別はセルのメモとプレビューに出す。

過去バージョンで付けたタグは、再実行時に `stripTag()` で除去される。

## プレビューと適用を分ける

シートには自動チェック機能やHPバーの数式が入っており、壊すと復旧が面倒。

`_CORRECTION` シートに差分を出し、**チェックを入れた行だけ**反映する2段階にした。
元シートはプレビュー段階では一切触らない。

## 技名 + 発動元 でグループ化する

同じ技名でも発動元が違えば別物。
（例: そよそよダスターはシルキー本体とシルキーズ・ポンポンの両方が使い、性質が違う）

逆に、技IDでグループ化するのは細かすぎる。
すべってシャンプーボムは属性違いで3つのIDに分かれており、ID単位だとサンプルが足りなくなる。

## 認証情報はスクリプトプロパティに置く

`PropertiesService.getScriptProperties()` に保存する。
シートのセルに置くと、**PTメンバーと共有した瞬間に全員がキーを見られる**。

> ジェネレーター本体は V1 Client Key を `setting!A1` に置く作りになっている。
> 共有前提で使うなら注意。

## 次にやるなら

優先度順。

1. **複数ログのマージ** — 1トライぶんだと欠測が出る（ダストブロワーが0になったのはこれ）。
   複数pullを混ぜれば対象人数のバリエーションも増え、判定材料が増える
2. **計画 vs 実戦の差分チェック** — FFLogsは被弾時のバフを返すので、
   「計画ではここでリプライザルのはずが入っていなかった」を自動検出できる。
   軽減表を「作って終わり」から「回して改善する」ものに変えられる
3. **フェーズ分割** — 時間的に離れたクラスタを別の技として扱う
4. **DoT列の補正** — 現状Hit列のみ
5. **ジェネレーター作者への報告** — 複数対象技のずれは再現条件付きで説明できる。
   上流が直れば自分でメンテするものがゼロになる（最もレバレッジが高い）
